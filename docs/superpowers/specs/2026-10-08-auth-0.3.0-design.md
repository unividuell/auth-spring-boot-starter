# auth-spring-boot-starter 0.3.0: the `frontend` switch, test support, and both apps on 0.3.0 — Design

Date: 2026-10-08
Status: designed, approved by the user (brainstorming session)

## Goal

mobility-manager is the first app on the lib that is not its origin. It exposed two gaps, each backed
by evidence from two apps:

1. **The lib silently assumes a single-page app.** A server-rendered app has to undo three of its
   defaults in its own chain (401 → redirect, logout 204 → redirect, no request cache →
   `CookieRequestCache`). One of them is a trap: an app's `logoutSuccessUrl` is silently lost, because
   the lib's logout success handler wins. And a plain `CookieRequestCache` also remembers htmx POSTs,
   which the browser replays as a GET after sign-in and gets 405.
2. **spring-security-test's `csrf()` does not get along with the lib's cookie repository.** The
   post-processor replaces the shared `CsrfFilter`'s `tokenRepository` by reflection, for good, with
   `TestCsrfTokenRepository(new HttpSessionCsrfTokenRepository())` (spring-security-test 7.1.1,
   `SecurityMockMvcRequestPostProcessors.CsrfRequestPostProcessor`). Every later request in the same
   test context gets no `XSRF-TOKEN` cookie and creates a session. Every project has hit it: the lib
   (`@DirtiesContext` in three test classes), countdown (69 `csrf()` calls plus a `@DirtiesContext`
   workaround in `UserControllerTest`), mobility-manager (its own helper). Spring's own
   `authentication()` gets this right: it wraps the existing repository instead of replacing it.

0.3.0 closes both gaps. Both apps move to the 0.3.0 release as part of this work.

## Decisions from brainstorming

- **No default mode.** Every app states what it is: `unividuell.auth.frontend: spa` or
  `server-rendered`. Without it the app refuses to start. 0.3.0 breaks on purpose: countdown sets
  `frontend: spa`, mobility-manager `server-rendered`.
- **The name is `frontend`** (rejected: `client`, which reads like `spring.security.oauth2.client`;
  `mode`, which does not say of what).
- **`login-page`** is required for `server-rendered` and must be a page of the app; for `spa` it is
  refused.
- **Test support ships as its own artifact**, `auth-spring-boot-starter-test` (rejected: helpers in
  the production jar behind an optional dependency). The repository becomes a multi-module build.
- **The lib's Spring tests move to an unpublished `integration-tests` module** that depends on the
  starter and the test artifact like any app, so the lib tests itself with the tool it hands out
  (rejected: duplicating the helper privately in the starter; turning the dependency around, which
  would type `signedInAs` on `OAuth2User` and let the build shape the public API; compiling one
  source set into two modules with build-helper).
- **Versions:** release 0.2.0 at `6557d29` (exactly the build both apps run as `0.2.0-SNAPSHOT`),
  develop as `0.3.0-SNAPSHOT`, release `0.3.0`, move both apps to the release, then
  `0.4.0-SNAPSHOT`.
- **Moving both apps is part of the work**, countdown including all test `csrf()` calls.
  mobility-manager gets its move as a pull request stacked on
  [unividuell/mobility-manager#4](https://github.com/unividuell/mobility-manager/pull/4).
- Spec and plan live in the lib repository (no longer in countdown).

## 2 · The `frontend` switch

`AuthProperties` gains:

```kotlin
/** Who builds the pages: a single-page app in the browser, or the server. No default. */
val frontend: Frontend? = null,
/** server-rendered only: where anonymous requests and logout land. A page of the app. */
val loginPage: String? = null,

enum class Frontend { SPA, SERVER_RENDERED }
```

Configuration (Spring binds `spa` / `server-rendered` to the enum constants):

```yaml
unividuell:
  auth:
    frontend: server-rendered   # or: spa
    login-page: /login          # server-rendered only
```

### Startup checks

An eager bean (the `RoleAllowlist` pattern) refuses to start with a clear message when:

| Case | Message (in substance) |
|---|---|
| `frontend` is missing | `unividuell.auth.frontend is not set — say spa or server-rendered` |
| `server-rendered` without `login-page` (or blank) | `unividuell.auth.login-page is required for frontend server-rendered — a page of the app, e.g. /login` |
| `spa` with `login-page` | `unividuell.auth.login-page is set for frontend spa — a single-page app routes its own login page; remove it` |
| `login-page` is not a page of the app | `unividuell.auth.login-page '<value>' must be a page of the app: a path starting with / outside /login/ and /oauth2/` |

"A page of the app" means: starts with `/`, not with `//` or `/\`, contains no `?` or `#`, and is not
under the lib's prefixes `/login/` and `/oauth2/`. The bare `/login` is allowed. The reason for the
prefix rule: if logout lands on `/login/start`, production immediately starts the GitHub sign-in, and
as the app is already authorised there, the user is signed straight back in. Logout would do nothing.

### `spa`

Exactly the behaviour of 0.2.0: 401 for anonymous requests, `POST /logout` → 204, `NullRequestCache`.

### `server-rendered`

In the lib's customizer, instead of the single-page-app defaults:

| | Behaviour |
|---|---|
| anonymous request | 302 to `login-page` (`LoginUrlAuthenticationEntryPoint`), for htmx and fetch requests too |
| `POST /logout` | 302 to `login-page` (`SimpleUrlLogoutSuccessHandler`) |
| request cache | `CookieRequestCache` (no session) whose matcher accepts **page navigations** only: `GET` with `Sec-Fetch-Mode: navigate`; without the header (curl, MockMvc, very old browsers) a `GET` counts as a navigation. htmx and fetch send `Sec-Fetch-Mode: cors` and are not remembered. |
| `login-page` | `permitAll`, set by the lib; the app need not open it itself |

Everything else stays: `oauth2Login` with `/login/start`, CSRF through `CookieCsrfTokenRepository`,
the failure handler to `/login/start?error`, the picker. The lib knows nothing about htmx; it tells
navigations apart by the standard Fetch Metadata header.

**Out of scope:** the picker does not pick up the remembered deep link (it keeps `?redirect` and `/`);
no error page of its own in `server-rendered`; no htmx-specific behaviour such as `HX-Redirect`.

## 3 · The test artifact `auth-spring-boot-starter-test`

Package `org.unividuell.auth.test`, file `AuthRequestPostProcessors.kt`:

```kotlin
/** A browser signed in as [principal] the way the lib signs one in, holding a CSRF token. */
fun signedInAs(principal: AuthPrincipal): RequestPostProcessor

/** The CSRF token the way a browser holds it: the XSRF-TOKEN cookie, echoed in X-XSRF-TOKEN. */
fun withCsrfToken(): RequestPostProcessor

const val TEST_CSRF_TOKEN = "test-csrf-token"
```

- `signedInAs` sets, through Spring's `authentication(…)`, an
  `OAuth2AuthenticationToken(principal, principal.authorities, principal.provider)` — the shape both
  of the lib's sign-in doors produce — and combines it with `withCsrfToken()`.
- `withCsrfToken` adds the cookie to the request's existing cookies (never replaces them) and sets
  the header. Under the double-submit scheme the `CsrfFilter` only checks that cookie and header are
  equal, so a fixed test token is legitimate and runs through the real production mechanism.
- Its KDoc explains why not `csrf()`.
- The app builds the `AuthPrincipal` itself (public constructor). No builder.
- Dependencies: the starter and `spring-security-test` (compile scope, so apps get it transitively).
  No Mockito. Apps add the artifact with `<scope>test</scope>`.

## 4 · The lib's integration tests use the test artifact

- The 18 `with(csrf())` calls in `TestLoginTest`, `TestLoginLockedTest` and `TestLoginAbsentTest`
  become `with(withCsrfToken())`. None uses `useInvalidToken()`; tests that expect 403 send no
  token, so no invalid-token variant is needed.
- Comments and KDoc that explain the `csrf()` trap (`AnonymousSessionTest`, `ProviderLoginTest`,
  `SpaContractTest`) are rewritten; `@DirtiesContext` goes wherever its only reason was that trap. A
  test that needs a fresh context for another reason keeps it, with that reason in the comment.
- The test application sets `frontend: spa`; the `server-rendered` tests run in their own context.
- **Test support's own tests** (against the same `TestApplication`): with `signedInAs(p)` a `POST`
  goes through and `GET /api/me` shows `p.id`; with `withCsrfToken()` alone (anonymous) a `POST`
  answers 401 — CSRF passed, sign-in missing; with no token, 403; existing cookies survive; and
  **after** a `signedInAs` request, an anonymous `GET` in the same context creates no session and
  still gets the `XSRF-TOKEN` cookie — the property `csrf()` destroys.
- **Startup checks:** one test per row of the table in section 2.
- **`server-rendered`:** an anonymous `GET` → 302 to `login-page`; `login-page` is reachable
  anonymously; `POST /logout` → 302 to `login-page`; an anonymous navigation `GET` sets the
  request-cache cookie, while an anonymous `POST` and a `GET` with `Sec-Fetch-Mode: cors` do not;
  after a provider sign-in the browser lands on the remembered deep link; anonymous requests still
  create no session.

## 5 · The lib's README

- "Use it": current version, `frontend` as required with an example for each value, the test artifact
  as a second dependency.
- "The SPA contract" applies to `frontend: spa`; add: do not configure `logout {}` in your own chain —
  it is silently lost.
- New "Server-rendered apps": the `login-page` rules and why (logout to `/login/start` signs straight
  back in), the request cache remembering navigations only, the CSRF pattern: forms through
  `th:action`, htmx through `hx-headers` with `X-XSRF-TOKEN` on `<body>`.
- New "Testing": `signedInAs`, `withCsrfToken`, why not `csrf()`. The profile note: an active test
  profile needs a key like any other profile — switch the test login off and register a client, or
  test without a profile.
- "Refuses to start when": the new cases from section 2.
- "Releasing": multi-module; the `deploy` command stays, and an app's `maven-repo/` then holds the
  parent, the starter and the test artifact. Moving an app to a new release deletes the old version's
  directories there.
