# auth-spring-boot-starter 0.3.0: `frontend`-Schalter, Test-Support, Umstieg der Apps — Design

Datum: 2026-10-08
Status: entworfen, vom User abgenommen (Brainstorming-Session)

## Ziel

mobility-manager ist die erste App, die die Lib nutzt, ohne ihr Ursprung zu sein. Dabei zeigten sich
zwei Lücken, beide mit Belegen aus zwei Apps:

1. **Die Lib setzt stillschweigend eine SPA voraus.** Eine server-gerenderte App muss drei Vorgaben
   in ihrer eigenen Chain zurückdrehen (401 → Redirect, Logout-204 → Redirect, kein Request-Cache →
   `CookieRequestCache`). Eine davon ist eine Falle: Ein `logoutSuccessUrl` der App geht still
   verloren, weil der Logout-Handler der Lib gewinnt. Und der `CookieRequestCache` merkt sich auch
   htmx-POSTs, die nach dem Login als GET mit 405 enden.
2. **Spring Security Tests `csrf()` verträgt sich nicht mit dem Cookie-Repository der Lib.** Der
   Post-Processor ersetzt per Reflection das `tokenRepository` des geteilten `CsrfFilter` dauerhaft
   durch `TestCsrfTokenRepository(new HttpSessionCsrfTokenRepository())` (spring-security-test 7.1.1,
   `SecurityMockMvcRequestPostProcessors.CsrfRequestPostProcessor`). Jeder spätere Request im selben
   Testkontext bekommt kein `XSRF-TOKEN`-Cookie mehr und legt eine Session an. Das hat schon jedes
   Projekt getroffen: die Lib (`@DirtiesContext` in drei Testklassen), countdown (69 `csrf()`-Aufrufe
   plus ein `@DirtiesContext`-Workaround in `UserControllerTest`), mobility-manager (eigener Helper).
   Springs `authentication()` macht es richtig: Es umhüllt das vorhandene Repository, statt es zu
   ersetzen.

0.3.0 schließt beide Lücken. Beide Apps steigen direkt auf das Release 0.3.0 um.

## Entscheidungen aus dem Brainstorming

- **Kein Default für den Modus.** Jede App sagt, was sie ist: `unividuell.auth.frontend: spa` oder
  `server-rendered`. Fehlt der Schalter, startet die App nicht. 0.3.0 bricht also bewusst: countdown
  muss `frontend: spa` setzen, mobility-manager `server-rendered`.
- **Name `frontend`** (verworfen: `client`, kollidiert gedanklich mit `spring.security.oauth2.client`;
  `mode`, sagt nicht wovon).
- **`login-page`** ist bei `server-rendered` Pflicht und muss eine eigene Seite der App sein, bei
  `spa` ist sie verboten.
- **Test-Support als eigenes Artefakt** `auth-spring-boot-starter-test` (verworfen: Helper im
  Produktions-Jar mit optionaler Dependency). Das Repo wird dafür Multi-Modul.
- **Versionen:** 0.2.0 wird auf `6557d29` released (genau der Stand, den beide Apps als
  `0.2.0-SNAPSHOT` nutzen), die Arbeit läuft als `0.3.0-SNAPSHOT`, wird als `0.3.0` released, beide
  Apps steigen auf das Release um, danach `0.4.0-SNAPSHOT`.
- **Umstieg beider Apps gehört dazu**, countdown inklusive Umstellung aller Test-`csrf()`.
- Spec und Plan liegen im Lib-Repo (nicht mehr in countdown).

## 1 · Versionen und Modulstruktur

**Release 0.2.0** auf `main` (wie 0.1.0, nach README „Releasing“): `versions:set 0.2.0`, Commit
„Release 0.2.0“, Tag `v0.2.0`, dann `versions:set 0.3.0-SNAPSHOT`, Commit „Start 0.3.0-SNAPSHOT“.
In die Apps wird 0.2.0 nicht deployt, sie springen direkt auf 0.3.0.

**Multi-Modul.** Die oberste `pom.xml` wird `org.unividuell:auth-spring-boot-starter-parent`
(Packaging `pom`; Spring-Boot-Parent `4.1.1`, Kotlin-Plugin, Properties, Release-Profil, Metadaten).
Darunter:

| Modul | Inhalt |
|---|---|
| `auth-spring-boot-starter/` | der heutige Code samt Tests, per `git mv` (Historie bleibt) |
| `auth-spring-boot-starter-test/` | Test-Support (Abschnitt 3); hängt am Starter und an `spring-security-test` |

- `deploy` vom Root legt drei Artefakte in das `maven-repo/` einer App: Parent-POM, Starter,
  Test-Artefakt. Die Parent-POM muss mit, weil die Modul-POMs sie referenzieren.
- CI (`./mvnw -B verify`) bleibt unverändert und baut den Reactor.
- `src/javadoc-placeholder/` gehört zum Release-Profil; es wandert in jedes Modul, das ein Jar
  veröffentlicht (Central verlangt ein Javadoc-Jar pro Artefakt).

## 2 · Der Schalter `frontend`

`AuthProperties` bekommt:

```kotlin
/** Who builds the pages: a single-page app in the browser, or the server. No default. */
val frontend: Frontend? = null,
/** server-rendered only: where anonymous requests and logout land. An app page. */
val loginPage: String? = null,

enum class Frontend { SPA, SERVER_RENDERED }
```

Konfiguration (Spring bindet `spa` / `server-rendered` auf die Enum-Konstanten):

```yaml
unividuell:
  auth:
    frontend: server-rendered   # or: spa
    login-page: /login          # server-rendered only
```

### Startup-Checks

Eine eager Bean (Muster wie `RoleAllowlist`) verweigert den Start mit klarer Meldung, wenn:

| Fall | Meldung (sinngemäß) |
|---|---|
| `frontend` fehlt | `unividuell.auth.frontend is not set — say spa or server-rendered` |
| `server-rendered` ohne `login-page` (oder leer) | `unividuell.auth.login-page is required for frontend server-rendered — an app page, e.g. /login` |
| `spa` mit `login-page` | `unividuell.auth.login-page is set for frontend spa — a single-page app routes its own login page; remove it` |
| `login-page` ist kein eigener Pfad der App | `… must be an app page: a path starting with / outside /login/ and /oauth2/` |

„Eigener Pfad“ heißt: beginnt mit `/`, nicht mit `//` oder `/\`, enthält kein `?`/`#`, liegt nicht
unter den Lib-Präfixen `/login/` und `/oauth2/`. Das nackte `/login` ist erlaubt. Grund für die
Präfix-Regel: Landet der Logout auf `/login/start`, startet in production sofort der GitHub-Login, und
weil die App dort schon autorisiert ist, ist man gleich wieder angemeldet. Der Logout wäre wirkungslos.

### `spa`

Exakt das Verhalten von 0.2.0: 401 für anonyme Requests, `POST /logout` → 204, `NullRequestCache`.

### `server-rendered`

Im Customizer der Lib, statt der SPA-Vorgaben:

| | Verhalten |
|---|---|
| anonymer Zugriff | 302 auf die `login-page` (`LoginUrlAuthenticationEntryPoint`), auch für htmx/fetch |
| `POST /logout` | 302 auf die `login-page` (`SimpleUrlLogoutSuccessHandler`) |
| Request-Cache | `CookieRequestCache` (keine Session) mit Matcher **„Seitennavigation“**: `GET` und `Sec-Fetch-Mode: navigate`; fehlt der Header (curl, MockMvc, sehr alte Browser), gilt ein `GET` als Navigation. htmx/fetch schicken `Sec-Fetch-Mode: cors` und werden nicht gemerkt. |
| `login-page` | `permitAll` durch die Lib; die App muss sie nicht selbst freigeben |

Alles andere bleibt gleich: `oauth2Login` mit `/login/start`, CSRF über `CookieCsrfTokenRepository`,
der Failure-Handler auf `/login/start?error`, der Picker. Die Lib kennt kein htmx; die Unterscheidung
läuft über den Standard-Header Fetch Metadata.

**Nicht im Umfang:** Der Picker übernimmt den gemerkten Deep-Link nicht (bleibt bei `?redirect`
bzw. `/`); keine eigene Fehlerseite im server-gerendert-Modus; keine htmx-Sonderbehandlung (etwa
`HX-Redirect`).

### Tests im Starter

- Je ein Test pro Startup-Check-Zeile.
- `spa`: die bestehenden SPA-Tests bleiben grün, die Test-App setzt `frontend: spa`.
- `server-rendered` (eigener Kontext über eine zweite Test-Konfiguration bzw. Properties): anonymer
  `GET` → 302 auf die `login-page`; die `login-page` selbst ist anonym erreichbar; `POST /logout` → 302
  auf die `login-page`; ein anonymer Navigations-`GET` setzt das Request-Cache-Cookie, ein anonymer
  `POST` und ein `GET` mit `Sec-Fetch-Mode: cors` setzen es nicht; nach einem Provider-Login landet
  man auf dem gemerkten Deep-Link; anonyme Requests legen weiterhin keine Session an.

## 3 · Das Test-Artefakt `auth-spring-boot-starter-test`

Paket `org.unividuell.auth.test`, Datei `AuthRequestPostProcessors.kt`:

```kotlin
/** A browser signed in as [principal] the way the lib signs one in, holding a CSRF token. */
fun signedInAs(principal: AuthPrincipal): RequestPostProcessor

/** The CSRF token the way a browser holds it: the XSRF-TOKEN cookie, echoed in X-XSRF-TOKEN. */
fun withCsrfToken(): RequestPostProcessor

const val TEST_CSRF_TOKEN = "test-csrf-token"
```

- `signedInAs` setzt per Springs `authentication(…)` ein
  `OAuth2AuthenticationToken(principal, principal.authorities, principal.provider)` — die Form, die
  beide Login-Wege der Lib erzeugen — und kombiniert das mit `withCsrfToken()`.
- `withCsrfToken` hängt das Cookie an die vorhandenen Cookies an (überschreibt sie nicht) und setzt
  den Header. Beim Double-Submit-Verfahren prüft der `CsrfFilter` nur Gleichheit von Cookie und
  Header; ein festes Test-Token ist daher legitim und läuft durch den echten Produktionsmechanismus.
- Die KDoc von `withCsrfToken` erklärt, warum nicht `csrf()`.
- Den `AuthPrincipal` baut die App selbst (öffentlicher Konstruktor). Kein Builder.
- Dependencies: Starter + `spring-security-test` (compile; kommt so transitiv in die Apps). Kein
  Mockito. Apps binden das Artefakt mit `<scope>test</scope>` ein.

**Eigene Tests** gegen eine Mini-App im Modul (`frontend: spa`, ein GET-, ein POST-Endpunkt):
`signedInAs(p)` → `POST` durch, `GET /api/me` zeigt `p.id`; nur `withCsrfToken()` (anonym) → `POST`
401 (CSRF bestanden, Login fehlt); ohne Token → 403; vorhandene Cookies bleiben erhalten; **nach**
einem `signedInAs`-Request legt ein anonymer `GET` im selben Kontext keine Session an und bekommt
weiterhin das `XSRF-TOKEN`-Cookie.

## 4 · Eigene Tests der Lib ohne `csrf()`

Das Starter-Modul kann das Test-Artefakt nicht nutzen (das hängt am Starter; umgekehrt entstünde ein
Maven-Zyklus). Deshalb:

- Ein privater Test-Helper im Starter (`TestCsrf.kt`, ~10 Zeilen) mit gültigem Token (Cookie =
  Header) und einer Variante mit abweichendem Token (Ersatz für `csrf().useInvalidToken()`).
- Alle `csrf()` in den Starter-Tests (22 Aufrufe in 6 Klassen) werden ersetzt.
- `@DirtiesContext` fällt dort weg, wo es nur wegen der `csrf()`-Falle steht (`AnonymousSessionTest`,
  `ProviderLoginTest`, `SpaContractTest`); wo ein Test einen frischen Kontext aus anderem Grund
  braucht, bleibt es mit eigenem Grund im Kommentar.

## 5 · README der Lib

- „Use it“: aktuelle Version, `frontend` als Pflicht mit Beispielen für beide Werte, das
  Test-Artefakt als zweite Dependency.
- „The SPA contract“ gilt für `frontend: spa`; dazu: in der eigenen Chain kein `logout {}`
  konfigurieren — es geht still verloren.
- Neu „Server-rendered apps“: `login-page`-Regeln samt Begründung (Logout auf `/login/start` meldet
  sofort wieder an), Request-Cache nur für Navigationen, CSRF-Muster: Formulare mit `th:action`,
  htmx per `hx-headers` mit `X-XSRF-TOKEN` am `<body>`.
- Neu „Testing“: `signedInAs`, `withCsrfToken`, warum nicht `csrf()`. Profil-Hinweis: Ein aktives
  Test-Profil verlangt einen Key wie jedes andere Profil — entweder den Test-Login abschalten und einen
  Client registrieren, oder ohne Profil testen.
- „Refuses to start when“: die neuen Fälle aus Abschnitt 2.
- „Releasing“: Multi-Modul; der `deploy`-Befehl bleibt, das `maven-repo/` enthält danach Parent,
  Starter und Test-Artefakt. Ein Release-Wechsel in einer App löscht das alte Versionsverzeichnis.

## 7 · Umstieg countdown auf 0.3.0

Feature-Branch von `develop` (countdown-Konvention: Rebase, nie Merge), PR gegen `develop`.

- `core/maven-repo/`: das Verzeichnis `0.2.0-SNAPSHOT` löschen, 0.3.0 deployen (Parent, Starter,
  Test-Artefakt).
- `core/pom.xml`: `unividuell-auth.version` → `0.3.0`, Test-Artefakt mit `<scope>test</scope>`.
- `unividuell.auth.frontend: spa` in `core/src/main/resources/application.yaml` **und**
  `core/src/test/resources/application.yaml` — Letztere ersetzt die Haupt-Datei auf dem
  Test-Klassenpfad, statt sie zu überlagern.
- Tests: alle 69 `with(csrf())` → `with(withCsrfToken())` (12 Klassen), Import
  `org.unividuell.auth.test.withCsrfToken` statt Springs `csrf`. `TestPrincipals.principalFor` bleibt
  (App-spezifisch: `User` → `AuthPrincipal`). In `UserControllerTest` fällt das
  `@DirtiesContext(BEFORE_METHOD)` samt Kommentar weg — es existiert nur wegen der `csrf()`-Falle.
- Doku: `.claude/guidelines/dependency-updates.md` (Release statt Snapshot, drei Artefakte im
  `maven-repo/`), `.claude/guidelines/security-and-auth.md` (`frontend: spa`; Tests mit
  `withCsrfToken`/`signedInAs`, nie `csrf()`).
- Verifikation: die volle Testsuite (Testcontainers/Postgres, braucht Docker) grün; lokal starten
  und Picker-Login plus eine mutierende SPA-Aktion im Browser.
